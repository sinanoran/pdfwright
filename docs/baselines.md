# Baselines

Numbers measured on 22 November 2026, on the maintainer's Windows machine, `Release`. The Playwright and Skia rows are one run each (21 November); the Pdfwright cold rows are the median of 30 fresh processes and the warm rows the median of 100 runs in one process. They
are **baselines to beat, not benchmarks**: the point is the order of magnitude, and the method.

## The scenario

A table of 1,000 rows and 6 columns (`Row {r} cell {c} text`), A4 portrait, a repeated header row, about
20 pages. The data is generated by `Scenarios/TableData.cs` in the benchmark project, and the Playwright
script (`Baselines/pw.cjs`) builds the same table as HTML.

## Pdfwright's own measurement

Pdfwright is measured with the harness in `benchmarks/Pdfwright.Benchmarks`, through the public API only (`PdfDocument`, `Table`, `Drawing`), with the Noto Sans and Noto Sans Arabic fonts of the test project.

**The machine.** AMD Ryzen 9 5900HX (8 cores, 16 threads), 31.4 GB RAM, Windows 11 (10.0.26300), .NET SDK 11.0.100 building `net10.0`, run on the .NET 10 runtime (10.0.15 is the latest 10.x installed), `Release`. **The runtime setup is the default one**: not ReadyToRun, not native AOT, framework-dependent, tiered compilation and Dynamic PGO at their defaults (see the note on both below).
**Free memory was low and moved a lot.** On 22 November `Available MBytes` was 1,104 MB when the work began and stayed between about 0.6 and 7.5 GB during the 30 minutes waited for it to reach 10 GB (it never did). Before each measurement it was: 5,849 MB (the runtime baseline), 4,963 MB (cold table, first set), 2,080 MB (cold report, first set), 933 MB (warm table), 4,803 MB (warm report), 6,861 MB (cold table, the set below), 3,573 MB (cold report, the set below) and 3,257 MB (runtime baseline, the set below); 2,790 MB after the last. Every number below was taken under that memory pressure, with other programs open: treat the times as an upper bound for a quiet machine, and the memory figures as what the process used, not what the machine had.

**The numbers move with the machine's memory state, a lot.** The same build gave a cold table p50 of 1,888 ms in one set of 30 runs and 2,095 ms in the next, a few minutes later; a reviewer measured 1.95 to 2.13 s on another day; the first version of this page, on 21 November with 4 to 6 GB free, gave 1.50 s; and runs of 10 in a row of the same build gave 3.6 s, 1.8 s and 1.5 s as the free memory went from 2.2 GB to 7 GB to 0.6 GB. The runtime baseline moved between 84 and 149 ms (wall) in the same way. Read the cold times as "between 1.5 and 2.1 s on this machine, depending on its memory state", not as a figure to the millisecond.

**Shaping fast paths, 22 November 2026 (output unchanged).** HarfBuzz shaping was the largest part of laying out a cell (about 25 microseconds and 5 KB per cell in a profile of the table). The shaper now reuses one HarfBuzz buffer per thread and reads the glyphs through spans, text that is only printable ASCII (a tab, shaped as a space, allowed) skips the bidi algorithm, the script itemizer and the grapheme breaker (it has one level, one script and one cluster per character), code points are read without lists, and a run that is a whole text (shaped with no context) is cached per font, keyed on text, direction, script and language, up to 2,048 runs of at most 256 characters, locked, emptied when full (worst case about 11 MB for each font; the cache lives as long as the `FontCollection` and keeps the cached strings alive). A run longer than 4,096 UTF-16 units is shaped in a temporary HarfBuzz buffer instead of the per-thread one, and a per-thread buffer that has grown past that is freed, so no thread keeps native memory in proportion to its longest text. A test shapes and lays out the whole corpus and 800 random texts with the paths off and on and compares every glyph and position, and builds the page corpus both ways and compares the bytes; the golden files are not regenerated. The build before and the build after, alternating on the same machine, Release, `net10.0`, free memory 3.6 to 6.9 GB (`Available MBytes`, 4,477 MB after the last set; under the 10 GB the method asks for, and 30 minutes of waiting did not raise it, so the times are noisy): scenario A warm p50 146 ms to 136 ms (the 146 ms against the 212 to 355 ms of the same build in the paragraph above is measurement noise from the free memory of the machine, so compare the before and after of one paragraph, not across them), allocation 82.3 MB to 59.0 MB per run; scenario B warm p50 34 ms to 22 ms, 11.3 MB to 8.1 MB; scenario A cold p50 1,177 ms to 1,044 ms, scenario B cold p50 510 ms to 520 ms (no change within noise); peak working set 52 MB to 52 MB (A) and 48 MB to 47 MB (B). The text of the table's cells (`Row 12 cell 3 text`) is nearly all different, so the cache does not help it; it helps documents that repeat values.

The change: the line breaker's and the grapheme breaker's scratch arrays and the `State`'s arrays come from `ArrayPool<T>.Shared` and are given back when the layout is built (an array of up to 4,096 elements comes from the shared pool and may stay there until the runtime trims the pool at a full garbage collection; a longer one is allocated, never pooled, and collected like any other, so a very long text does not leave arrays sized for it in the pool; a `State` is never shared: it lives inside one `Layout` call. The limit was added after the measurements below, which were not repeated: a cell of the table is far shorter than 4,096 characters, so it does not change what is rented for it); a page's content buffer is emptied and used for the next page of the same save (the save's own, so never shared between documents or threads; kept only up to 1 MB); the draw reads the fonts of the lines with a loop and two arrays of the renderer instead of a set, and keeps each font's embedded form in an array; `FontCollection.Snapshot.Order` finds a family by its spelling before it builds an upper-case key; a paragraph of one style over its whole text (a table cell) skips the tables of shaping groups and the string builder; a line of one piece skips the visual-order step. **Word-by-word shaping, 23 November 2026 (output unchanged).** The profile above put HarfBuzz at about 41 ms of the table: its cells are nearly all different texts, so the cache of whole texts never hits. Printable ASCII in a font whose layout rules never involve the space glyph is now cut at the spaces and each word is shaped alone and cached per font (as a browser shapes word by word); the glyphs are the same as shaping the whole text, which tests check glyph by glyph (random printable ASCII, every pair and triple of characters around a space, the benchmark's cells, prose, many threads) and byte by byte on whole documents. So of the table's 2,095 ms about 150 ms are the runtime starting, and the working set of 52 MB is **30 MB above the baseline of 22 MB, against the plan's target of 25 MB** for the increase (the ten-page report: 49 MB, 27 MB above).

**ReadyToRun and tiered PGO, indicative only.** The numbers above are the default JIT setup. Runs of 10 of the table in a row, in conditions that were not the same from one set to the next (free memory between 0.6 and 7 GB), gave a cold p50 of 3,594 ms and later 1,821 ms with the default build, 1,491 ms with `DOTNET_TieredPGO=0`, and 1,581 ms for a build published with `-p:PublishReadyToRun=true`; a reviewer saw about 1.8 s (ReadyToRun) and 1.35 s (`DOTNET_TieredPGO=0`) against about 2.0 s by default, in the same noisy conditions. So both change the cold number, probably by 10 to 30 percent, but the noise on this machine is as large as the effect and this was not measured properly. The later paired sets of 22 November 2026 (above, in the layout-state section: two sets of 30 fresh processes each, alternating, 33 percent on the means) point the same way and are the better figure, but they too were taken at 4.2 GB free and are as noisy: the same default build measured 1.01 to 1.11 s in the table and 1.57 s there. They are settings for the application, not for the library.

**After the allocation-free content writing (22 November 2026, same machine and build settings, `Release`, .NET 10 runtime).** The numbers, operators and glyph codes of a page's content are now written straight into its byte buffer, and the glyph order of a run no longer uses LINQ; the output is byte for byte the same (513,897 bytes for A, 102,715 for B). Warm, 100 runs after 10 warm-up, a full GC between runs, A and B each measured before and after in the same sitting:

| | Before (re-measured in the same sitting) | After |
|---|---|---|
| A, managed allocation per run | 187.7 MB | **85.5 MB** |
| B, managed allocation per run | 24.0 MB | **12.2 MB** |
| A, warm p50 | 335 ms (412 and 358 ms in two later sets) | 319 to 365 ms (365 ms and 319 ms in two sets) |
| B, warm p50 | 47 ms (66 and 100 ms in later sets) | 40 to 86 ms (86 ms and 40 ms) |

**Free memory was low** (Available MBytes: 4.7 to 9.1 GB before the sets, 3.4 to 4.7 GB while waiting for 10 GB, which it never reached in 30 minutes), and the times moved by a factor of two from one set to the next with it: the allocation figures are exact, the times only say "not slower, probably 10 to 20 percent faster". Taken only in the quietest set (4.7 GB), A went from 412 to 319 ms and B from 66 to 40 ms.

**Why the warm loop's 347 ms is not 473 ms (the first version) and not BenchmarkDotNet's 368 ms.** The first version of the warm loop did not collect between iterations, so the collections of the run's 188 MB of garbage fell inside the timed runs (473 ms against BenchmarkDotNet's ~368 ms, which collects between iterations). The loop now calls `GC.Collect()` between iterations, outside the timing. The warm figures are therefore without the collection cost a long-running server would pay now and then.

**What the numbers say, and what they do not.** The p50 is the true median (the mean of the two middle values of an even count); the p95 of 30 runs is the 29th value (nearest rank), nearly the maximum: it is a feel for the spread, not a tight estimate. The 30 cold runs were made back to back, so the operating system's file cache was warm for all but the first process of a session. A "cold" process here is a fresh .NET process: it pays the JIT, and does not use ReadyToRun or native AOT. The wall time is taken by the parent with `WaitForExit` (the working set is sampled on another thread, so no sleep adds to it). The warm figures include building the document and saving it to memory, and not loading the fonts (loaded once).

**Comparison with the Playwright and Skia rows.** Order of magnitude only. Those were one run each, on the same machine on the previous day, and measured differently: Playwright's 2,048 ms is the script's own time from the browser launch to the end of `page.pdf` (node's start and the browser's close excluded), its memory is the highest sampled working set of the whole process tree, and the Skia spike's method is not documented beyond "cold process" and "peak". The Pdfwright cold time here is a parent process timing a child from its start to its exit, runtime start included, and its memory is that process's own `PeakWorkingSet64`. The layouts differ too (margins, padding, fonts, above). With that said: for the 1,000-row table Pdfwright (about 2 s, 52 MB) is in the same range of time as the browser (about 2 s) and nowhere near the Skia spike (279 ms), uses a tenth of the browser's memory and about twice the Skia spike's, and writes a file 3.3 times the browser's (154 KB) and slightly smaller than the Skia spike's (590 KB).

**Against the targets of section 7 of the plan:** not met, see there.

## How to repeat the Playwright measurement

The two tools measure different things, so use both:

<!-- snippet: none -->
```bash
cd benchmarks/Pdfwright.Benchmarks/Baselines
npm install playwright-core
# a Playwright "chromium_headless_shell" build (npx playwright install chromium-headless-shell)
export PW_CHROME=/path/to/chrome-headless-shell      # without it, pw.cjs launches full Chromium, not the shell above

# Memory (Windows): the highest working set sampled over the whole process tree, browser included
pwsh sample.ps1 pw.cjs 1000

# Wall time of a fresh process (any OS), median of 10: includes the script's 1.5 s pause before it closes the browser,
# so it is not the 2,048 ms of the table; and its peak working set is that of `node` alone, not of the browser
dotnet run -c Release --project ../ -- cold --runs 10 -- node pw.cjs 1000
```

The `cold` verb is for Pdfwright itself: one process, no children, so its figures are complete.
`pw.cjs` prints its own breakdown (launch, content, pdf) as JSON, which is where the table's 442, 901 and 705 ms
come from.

## How to repeat the Pdfwright measurement

Check the machine first: close other programs and read the free memory, which is part of the result (PowerShell: `(Get-Counter '\Memory\Available MBytes').CounterSamples.CookedValue`). Then, from the repository root:

<!-- snippet: none -->
```bash
dotnet build benchmarks/Pdfwright.Benchmarks -c Release -nodeReuse:false -m:1
cd benchmarks/Pdfwright.Benchmarks/bin/Release/net10.0

# Scenario A (1,000-row table) and B (ten-page report), cold: 30 fresh processes each
./Pdfwright.Benchmarks cold --runs 30 -- ./Pdfwright.Benchmarks once table table.pdf
./Pdfwright.Benchmarks cold --runs 30 -- ./Pdfwright.Benchmarks once report report.pdf

# Warm, in one process: 100 runs after 10 warm-up runs
./Pdfwright.Benchmarks warm table --runs 100 --warmup 10
./Pdfwright.Benchmarks warm report --runs 100 --warmup 10

# The runtime baseline: a process that only starts, 30 times (and, for ReadyToRun, publish and repeat the cold runs with the published program)
./Pdfwright.Benchmarks cold --runs 30 -- ./Pdfwright.Benchmarks start
dotnet publish ../../../Pdfwright.Benchmarks.csproj -c Release -r win-x64 --self-contained false -p:PublishReadyToRun=true -o r2r -nodeReuse:false -m:1

# Warm time and allocations with BenchmarkDotNet (a quick, rough job; leave --job short out for the full one)
./Pdfwright.Benchmarks bench --filter "*" --job short
```

On Windows the program is `Pdfwright.Benchmarks.exe`. `DOTNET_TieredPGO=0` in the environment turns tiered PGO off for a run. `once` prints one JSON line (time since the process started, its own peak working set, bytes, pages), and `cold` takes the peak from it, so the figures are the process's own. The benchmark project is built by `dotnet build Pdfwright.slnx` so it cannot rot; CI builds it and does not run it.
